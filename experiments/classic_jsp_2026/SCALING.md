# Running this on a bigger machine

Everything measured in this directory was produced on 4 cores, and the binding
constraint was never solution quality -- it was **statistical power**. Four
configurations of the local search landed within 0.07 percentage points of each
other on `ta01`-`ta10` and nothing could be concluded; the 30x20 comparison
reached p = 0.084 and still could not close. More cores buy exactly the thing
that was missing.

> **Two things have changed since this file was written.**
>
> `experiment/classic-jsp-crisp` replaced the interval arithmetic with a crisp
> integer time and runs **2.00x** as many generations in the same wall clock.
> That does *not* make the experiments below cheaper: they stop on wall-clock
> time, so they cost the same CPU-hours and spend them on twice the search. It
> is realisable as a saving only by taking step 2's advice and halving the
> budget, which now buys what the full budget used to.
>
> More important for the plans below: **two builds compared one after the other
> cannot be told apart on this machine below about 10 %.** The same binary,
> identical by md5, measured 4.122 and 3.812 gen/s in two batches. Comparisons
> of *builds* must use `scripts/paired_compare.sh`. Comparisons of
> *configurations* are safer -- they are judged on solution quality, which does
> not drift with the machine -- but their run counts still have to be decided in
> advance.

## Nothing needs changing to scale

`run_jsp.sh` sets `MAX_PARALLEL` from `nproc`, and each solver process is
single-threaded, so one process per core is the right setting. Override it only
to leave headroom on a shared machine:

```
MAX_PARALLEL=24 bash experiments/classic_jsp_2026/scripts/run_jsp.sh \
    experiments/classic_jsp_2026/setup/<setup>.txt <results-dir> ta41 ta42 ...
```

Re-running the same command resumes: an instance is skipped only when its
certificate holds every run the setup asks for, and one interrupted partway is
redone. A batch killed by a restart costs the runs it lost, nothing more.

## What to run, in order

### 1. The population collapse

This is the open question, and the only one where a real gain is plausible.

On `ta01` the population average reaches the best individual's value within 30
generations and the run then spends the rest of its budget on copies of one
solution. **Every change tried in this directory was inside the local search --
tenure bounds, longer searches, back-jump tracking -- and none of them helped.**
That pattern is what a binding constraint elsewhere looks like. The
`seeding-study` branch reached the same place from a different direction.

This is a design question before it is a compute one: restart or reinitialise on
collapse, diversity-preserving replacement, an explicit distance measure between
schedules. `StatisticsDiversity` already exists and is worth wiring into these
setups first, so that collapse is measured rather than inferred from the average
converging.

Cores help here only once there is something to compare.

### 2. Re-run the easy-instance comparison at a budget that is not wasted

`ta01`-`ta10` were compared at 60 s, and `convergence.py` shows the median run's
last improvement at 12 % of that. At 30 s with 40 runs -- the same CPU as 20 runs
at 60 s -- roughly one run in eight is affected and the sample doubles.

* Cost: 10 x 2 x 40 x 30 s = 6.7 CPU-hours.
* Worth doing whenever a new configuration needs evaluating, as the cheap first
  screen before spending anything on the open instances.

### 3. Give the hard instances the budget they want

16 % of `ta41`-`ta50` runs were still improving in the final tenth of 300 s, so
that budget truncates the search and part of the 6.4 % gap is the clock rather
than the algorithm.

* `ta41`-`ta50`, 1800 s, 10 runs, then re-run `convergence.py`: if runs still
  improve at 90 %, raise it again.
* Cost: 10 x 10 x 1800 s = 50 CPU-hours.
* This bounds how much of the gap is reachable by waiting, which is worth
  knowing before attributing any of it to the algorithm.

### Already answered -- do not repeat

**Back-jump tracking.** Settled on all 22 open instances: plain tabu is better at
the 5 % level on the 12 instances that were not used to generate the hypothesis,
and the two are indistinguishable over the whole set. The `ta41`-`ta50` result
that motivated it was a selection effect.

**Tabu tenure bounds** and **longer local searches**. Both null, both recorded in
the journal with the runs behind them.

### A method note for whatever comes next

Two of the three dead ends here were first reported as wins, from a subgroup or
from too few runs. The rule that would have caught both: **decide the instance
set and the number of runs before looking at the result, and test any hypothesis
generated by one subgroup on instances that were not used to generate it.** The
back-jump extension did exactly that and refuted it.

## What more cores will not do

Best known solutions on the open instances sit **3-5 % below** anything this
configuration produces. Those numbers come from decades of specialised
algorithms; no amount of parallelism closes that from here. Steps 1-3 are worth
doing because they answer questions that are actually open. Improving a
published result is not one of them.
